# Skill: extract-data (공고 데이터 정밀 추출 전담 파이프라인)

이 스킬은 공고문 원본(`document.md`)과 메타데이터(`api_meta.json`)로부터 청약 정보(일정, 조건, 단지, 평형 가격, 상세 서술)를 전수 분석하여 완제품 `data.json`을 작성하는 **순수 추출 전담 가이드라인**입니다.

⚠️ **절대 주의 (권한 분리 및 무결성 원칙 - Hard Guardrails)**:
- **[서브에이전트 전담 실행 원칙 (Mandatory Subagent)]**: 메인 에이전트는 메인 세션에서 직접 데이터를 추출하거나 스크립트를 돌려서는 안 되며, 반드시 `invoke_subagent`를 통해 `extract-data` 전용 서브에이전트를 호출하여 작업을 위임해야 합니다.
- **[오직 document.md 단일 소스 원칙]**: 에이전트는 데이터를 추출할 때 오직 사용자분이 검증해 둔 `document.md`만을 유일한 원본 소스로 사용해야 합니다. `docs/pdf/`나 첨부 엑셀(`.xlsx`)을 임의로 열어보거나 파싱하는 꼼수를 엄격히 금지합니다.
- **[임의 스크립트 작성 전면 금지 (No Scratch Scripting)]**: 데이터 추출·가공을 위해 `scratch/`나 임의 경로에 일회성 파이썬 스크립트(`.py`)를 작성하여 데이터를 일괄 파싱하거나 합성(날조)하는 행위를 영구히 금지합니다.
- **[1회 1공고 엄격 직렬화 원칙 (Strict 1-By-1)]**: 다건의 공고가 대기 중이더라도, 여러 공고를 루프로 일괄 처리하거나 배치로 묶는 행위를 전면 금지합니다. 반드시 단 1건의 공고 폴더만 타겟팅하여 완결한 후 다음 공고로 넘어가야 합니다.
- **[details 원본 라인 번호 인용 의무]**: `announcement_details` 7대 섹션 작성 시, 임의의 공통 템플릿 문안이나 가상의 표를 작성하는 행위를 전면 금지하며, 반드시 `document.md`의 실제 원본 출처 라인 번호(`L{Start}~L{End}`)를 각 섹션 상단에 주석 메타(`<!-- Source: document.md#L... -->`)로 명시해야 합니다.
- 이 스킬을 수행하는 에이전트는 **절대로 DB 적재 스크립트(`insert_loader.py`)를 실행하거나 DB를 직접 수정해서는 안 됩니다.**
- 데이터의 전수 검증 및 최종 DB 적재는 반드시 독립된 **`audit-data`** 스킬에 의해 수행됩니다.
- **[감사 불합격 시 정밀 재수정 의무]**: `audit-data` 감사 서브에이전트로부터 불합격(FAIL) 리포트가 인계된 경우, 지적된 오차(수치 불일치, 필드 누락 등)를 `document.md` 원본과 재대조하여 `data.json`의 결함 부위를 정밀 수정한 후 다시 감사를 의뢰해야 합니다.

## 1. 추출 단계별 수행 지침

### 0단계: 공고 유형 사전 판별 및 작업 분기 (Pre-Flight Notice Classification)
공고 분석을 시작하기 전, 에이전트는 반드시 판별 유틸리티를 1회 실행하여 공고의 유형과 기존 DB 적재 여부를 기계적으로 확정합니다:
```bash
python3 .agents/scripts/detect_announcement_type.py db-pipeline/docs/md/{공고_폴더}
```
위 스크립트가 반환한 JSON의 `action_type`에 따라 아래와 같이 작업 분기를 엄격히 적용합니다:

1. **[유형 A] 완전 신규 공고 (`action_type == "TYPE_A_NEW_ANNOUNCEMENT"`)**:
   - DB(`public_housing.db`)에 기존 공고가 존재하지 않는 순수 신규 공고.
   - **처리**: 표준 6대 핵심 필드 추출 (`Clean Title` 및 토큰 분할 빌드 준수).
2. **[유형 B] DB 기적재 정정/재공고 (`action_type == "TYPE_B_UPDATE_EXISTING"`)**:
   - 기존 공고가 DB에 이미 적재되어 있고, 정정/재공고 폴더가 들어온 경우.
   - ⚠️ **[동일 계보 검증 의무 — id 재사용 전 필수]**: 스크립트가 반환한 `title_match_warning`이 명시하듯, 이 판정은 제목 문자열 일치만으로 나온 것이라 **진짜 동일 공고 계보라는 보장이 아닙니다**. LH는 "OO지역 국민임대주택 예비입주자 모집" 같은 제목을 매달 재사용하는 정례모집이 있고(그때그때 단지 풀이 완전히 다름), 이 경우 제목만 같을 뿐 무관한 별개 회차인데도 TYPE_B로 나옵니다(실측 사례: 2026-09-20, "원주시지역 국민임대주택 예비입주자 모집" — 기존 id=120은 이미 서류제출까지 끝난 무관한 지난 회차였음). **id를 `data.json`에 쓰기 전에 반드시**:
       1. `existing_complexes`의 각 단지 `address`를, 이번 공고문(`document.md`)에 실제로 나열된 단지 주소와 하나씩 직접 대조한다.
       2. 겹치는 단지가 하나도 없거나, 기존 공고(`existing_announcement`)의 `announcement_schedules` 일정이 이번 문서의 일정과 완전히 동떨어져 있으면(예: 기존 건은 이미 서류제출까지 끝났는데 이번 문서는 완전히 새로운 신청접수 일정을 안내), **id를 재사용하지 말고 즉시 작업을 멈추고 메인 에이전트에게 이 사실을 보고**한다(감사로 넘기지 말 것). 이 경우 신규(TYPE_A)로 처리할지는 사람이 판단한다.
       3. 겹치는 단지가 실제로 확인되면 아래대로 정상 진행한다.
     - `title`: 스크립트가 반환한 `clean_title`을 사용하여 **기존 공고의 Clean Title을 100% 보존**합니다.
     - **[누적 규칙 #8 ID 보존 의무]**: 위 검증을 통과한 경우에만, 스크립트가 반환한 `existing_announcement.id`를 `data.json`의 `announcement.id`에 명시하며, `existing_complexes`의 기존 단지 ID(`complexes.id`)를 매칭하여 보존합니다.
     - **[필수] 최신 공고 URL 갱신**: `dtl_url`, `dtl_url_mob`은 구버전 공고 URL이 아닌, **정정공고 폴더 `api_meta.json`의 최신 공고 상세페이지 URL**을 100% 반영합니다.
     - **[필수] 문서 경로 갱신**: `doc_path`를 새 정정공고 폴더의 `document.md` 상대 경로로 갱신합니다.
     - **정정 내역 대조 반영**: 정정공고문 본문 및 주택목록을 대조하여 변경된 유닛/단지/일정을 정밀 교체합니다.
3. **[유형 C] 신규 공고와 정정공고가 `docs/md`에 동시 존재하는 공고**:
   - DB에는 둘 다 미적재 상태인데, `docs/md`에 원본 공고와 정정공고 폴더가 함께 있는 경우.
   - **처리**:
     - **최신 정정본 단일 채택**: 정정공고 폴더를 주 작업 대상으로 지정하여 **단 1건의 `data.json`만 빌드**합니다. (중복 공고 생성 원천 차단)
     - **원본 교차 보완**: 정정공고문에 변경된 호실만 있고 전체 주택목록/기준표가 생략된 경우, 원본 공고의 `document.md`를 교차 대조하여 완전체 `data.json`을 완성합니다.
     - **구버전 아카이빙**: 정정공고 빌드 완료 후, 원본 공고 폴더는 중복 적재 방지를 위해 즉시 `db-pipeline/docs/md/!old/`로 이동(아카이빙)합니다.

### 1단계: 원본 문서 및 메타데이터 완독
1. `db-pipeline/docs/md/{공고_폴더}/document.md` 전체를 완독합니다.
2. 첨부 주택목록 표 및 `api_meta.json`의 원본 데이터를 대조하여 다음 핵심 정보를 파악합니다:
   - 총 공급호수(공가) 및 총 모집 예비자수
   - 주택군(모집단위) 목록 및 소속 단지/호실
   - 가구원수별 소득 기준표, 자산 기준표, 배점 기준표 원문 표 위치

### 2단계: 6대 핵심 영역 data.json 빌드

⚠️ **[대형 공고 물리적 분할 빌드(Chunked Build) 규약 - LLM 토큰 한도 방지]**:
- 단지 수가 많거나 유닛 수가 많은 대형 공고의 경우, 에이전트가 50KB 이상의 거대 JSON 전문을 `write_to_file` 인자로 한 번에 출력하려 하면 **LLM 1회 출력 토큰 한도(Output Token Limit)에 걸려 출력이 강제 중단(cut-off)**됩니다.
- 규칙 기반 텍스트 파서(정규식)로 회귀하지 않고 **에이전트의 문맥 이해력(LLM)으로 정밀 추출하되**, 디스크 저장 시에는 반드시 **2단계 분할 조립(Chunked Build)** 방식을 적용합니다:
  - **1차 청크 작성**: 에이전트가 직접 분석한 `announcement`, `schedules`, `recruitment_groups`, `complexes` 데이터를 작성하여 1차 파일/딕셔너리로 저장.
  - **2차 청크 작성**: 에이전트가 직접 분석한 우선/일반 분리 `units` 및 컴팩트 `details`를 작성하여 1차 데이터에 병합(Merge)한 후 `data.json`으로 최종 direct dump 저장.
- 이렇게 하면 에이전트의 높은 지능과 문맥 판단력을 100% 활용하면서도 토큰 한도 에러를 완벽하게 차단할 수 있습니다.

#### ① `announcement` 추출 규약
- `title`: `[정정공고]`, `[정정]`, `(정정)`, `[재공고]` 등 시스템 접두사 노이즈를 100% 제거한 Clean Title.
- `institution`: `"LH", "SH", "GH", "iH", "HUG", "민간"` 중 1개로 엄격 정규화.
- `subscription_type`: `"매입임대", "행복주택", "국민임대", "영구임대", "공공분양", "장기전세"` 등 표준 유형.
- `region`: 대한민국 17대 광역지자체 표준 행정구역명 중 1개로 정제. (비표준 지자체명 사용 금지)
- `dtl_url`, `dtl_url_mob`: `api_meta.json`의 실제 URL 보존. **(정정공고의 경우 구버전 링크가 아닌 정정공고 `api_meta.json`의 최신 URL을 100% 반영)**
- `doc_path`: 정정공고 및 신규 공고를 막론하고 현재 작업 중인 폴더의 `document.md` 상대 경로 기록.
- `attributes`: **extract-data가 채우는 필드가 아닙니다.** 정정공고 이력(`correction_count`/`corrections`)을 `insert_loader.py`가 재적재 시점에 자동 기록하는 전용 필드이므로, `data.json`에서 임의로 값을 넣지 마십시오.

#### ② `schedules` 추출 규약
- 공고문 본문의 일정표에서 아래 6종 표준 `schedule_type`을 우선 사용합니다: `모집공고`, `신청접수`, `서류제출대상자발표`, `서류제출`, `당첨자발표`, `계약체결`.
- 원문 일정 항목이 이 6종에 명확히 대응되지 않는 경우(예: `주택열람`, `현장접수`, `입주지정기간` 등 기관별 특수 일정)에는 원문 표현을 그대로 `schedule_type`에 사용해도 됩니다 — 표준 6종을 억지로 끼워맞추지 마십시오.
- 날짜 포맷은 엄격히 `YYYY-MM-DD HH:MM:SS` 준수 (미정 시 null, 이 경우 `raw_text`에 원문 일정 문구를 그대로 남겨 프론트가 폴백으로 표시할 수 있게 합니다).
- 1순위/2순위 접수 일정이 다를 경우, `schedule_type`에 `"신청접수(1순위)"`처럼 순위를 병기하거나 `notes`에 명시하여 누락 없이 개별 레코드로 발췌합니다.

#### ③ `recruitment_groups` 추출 규약
- `name`: 공고문 표의 공식 주택군/모집단위명 (아파트형 단일 청약은 단지명 1:1, 매입임대는 공식 군 번호/지자체명).
- `supply_count`: 해당 주택군 소속 호실 합계 (`sum(recruitment_groups.supply_count) == 공고 총 공급호수`).
- `reserve_count`: 해당 주택군 예비자 모집인원 (`sum(recruitment_groups.reserve_count) == 공고 총 예비자수`).
- `region`: 해당 주택군이 위치한 행정구역명(시/군/구 단위). 공고문에 여러 지역이 섞인 광역 공고(예: 인천지역본부 통합 공고)에서 주택군별로 지역이 다를 때 채웁니다. 단일 지역 공고라 `announcement.region`과 동일하면 생략 가능.
- `notes`: 해당 주택군에만 적용되는 특이사항(예: "리츠형 배정분", "우선공급 전용 군")이 있을 때만 기록. 없으면 비워둡니다.

#### ④ `complexes` 추출 규약 (단지명 오염 원천 차단)
- **단지명(`name`) 추출 원칙**:
  - 마크다운/엑셀 표의 **공식 건물명/단지명 컬럼**을 최우선 사용합니다.
  - 도로명주소에서 임의로 잘라낼 때 `17(병점동)`, `9(동천동)`, `22(당동)` 같은 **지번, 건물번호, 동 번호 찌꺼기를 단지명으로 취급하는 것을 전면 금지**합니다.
  - **[단지명 추출 Before/After 정제 사례]**:
    - ❌ 오염 사례: `17(병점동)` $\rightarrow$ ⭕️ 올바른 명칭: `한길타워` (원문 표 '건물명' 컬럼 발췌)
    - ❌ 오염 사례: `9(동천동)` $\rightarrow$ ⭕️ 올바른 명칭: `수지동천더프라임` (원문 건물명)
    - ❌ 오염 사례: `(동천동 972, 101동)` $\rightarrow$ ⭕️ 올바른 명칭: `수지동천더프라임 101동`
    - ❌ 오염 사례: `12-1(본오동)` $\rightarrow$ ⭕️ 올바른 명칭: `본오동 더블루` (표의 주택명 복원)
- **물리적 분리**: 물리적으로 서로 다른 도로명주소에 위치한 주택은 반드시 독립된 complex로 분리 생성합니다.
- **단지 스펙 수록**: 본문 및 주택목록 표에서 난방방식(`heating_type`), 승강기 유무(`has_elevator`), 주차 대수/안내(`parking_info`)를 전수 발췌하여 채웁니다. (이유 없이 NULL 방치 금지)
- **`complex_type` 임의 해석 금지**: 원문 표에 건물유형/사업유형이 명시된 컬럼(예: "매입다가구", "매입다세대", "아파트", "연립주택", "다세대주택" 등)이 있으면 **그 문구를 그대로** 사용합니다. 표 헤더가 모호하거나(예: PDF 변환 과정에서 "지자체명" 같은 엉뚱한 헤더 밑에 실제로는 건물유형 값이 들어있는 경우) 값이 실제로 무엇을 뜻하는지 애매하면, 임의로 "아파트/연립주택/다세대주택" 중 하나로 의역하지 말고 원문 값 그대로 적재합니다. (실측 사례: 같은 건물을 서로 다른 시점에 추출하며 "연립주택"/"다세대주택"으로 각각 의역해 데이터 충돌이 발생함 — docs/dev/DOMAIN_MODEL.md 9장 참고)
- **`recruitment_group`(단지 기본 신청단위)**: 해당 단지 전체가 신청단위 하나에만 속하는 단순한 경우, 단지 레코드 자체에 `recruitment_group` 필드로 소속 주택군명을 지정합니다. 유닛마다 신청단위가 갈리는 경우는 여기서 지정하지 말고 §⑤의 유닛 단위 오버라이드를 사용하십시오.
- **`attributes`는 존재하지 않습니다**: `complexes.attributes` 컬럼은 완전 미사용 상태로 확인되어 2026-09-20 `010_drop_unused_complex_attributes.py`로 삭제되었습니다. `data.json`의 `complexes[]` 객체에 `attributes` 필드를 넣지 마십시오.

#### ⑤ `units` (housing_units) 추출 규약
- **`room_type`(평형/타입 구분 컬럼) 인식 규약**: 이 컬럼의 헤더명은 기관/공고유형별로 제각각입니다.
  263개 공고 실사 결과 다음 헤더들이 전부 같은 개념으로 쓰입니다 — 헤더에 이 중 **하나라도** 포함되면
  평형/타입 구분 컬럼으로 인식합니다: `신청유형`, `주택형`, `공급형별`, `주택 타입`, `평형`.
  절대 "신청유형"이라는 정확한 문자열만 찾지 마십시오(실측 시 8/263건뿐이었음, 대부분은 "주택형"/"공급형별" 사용).
  **표에 `순번`(행 번호) 컬럼과 이 평형구분 컬럼이 둘 다 있는 경우, 절대 혼동해서 순번 값을 `room_type`에 넣지 마십시오**
  (실측 사례: 순번 1,2,3...이 신청유형 대신 잘못 들어가 "1형"이 18~34㎡을 다 가리키는 오류가 발생함).
- **`recruitment_group`(신청단위) 단위 지정**: 한 단지 안에서 유닛마다 서로 다른 신청단위(모집단위)에
  속할 수 있습니다(예: 일반 배정분과 리츠형 배정분이 같은 건물 안에 공존). 이런 경우 `complexes[].recruitment_group`
  (단지 기본값)이 아니라 **유닛 객체 자체에 `recruitment_group` 필드를 직접 지정**하여 오버라이드하십시오.
  단순한 경우(단지 전체가 신청단위 하나)는 `complexes[].recruitment_group`만 지정하면 충분합니다.
- **`income_group` 원문 그대로 보존**: 입주순위(1~4순위, 가군/나군), 임대조건 시중시세 비율,
  실제 소득기준(%)이 원문에서 별도 표로 나뉘어 있어도 **`income_group` 필드 하나에 원문 표현을 그대로** 담으면
  됩니다(예: `"1·2순위 (시중시세 30% 수준)"`, `"소득 70% 이하 (건설형) / 105% 이하 (매입형)"`). 구조 분해는
  적재 스크립트가 자동으로 수행하므로, 여기서 값을 쪼개거나 요약하지 말고 원문 표현을 훼손 없이 옮기십시오.
- **`sale_price`(분양가, 공공분양/분양전환 전용)**: 보증금/월임대료 개념이 없고 분양가만 있는 공고(공공분양,
  분양전환)는 `deposit`/`monthly_rent`를 0으로 채우지 말고, `sale_price` 필드에 분양가(원 단위)를 기록하십시오.
- **우선공급 / 일반공급 분리 원칙**:
  - 공고문 원문 표에 공급호수가 `우선`과 `일반`으로 나뉘어 기재된 경우, 합산하지 않고 `supply_type`을 `"{공급유형}(우선)"`과 `"{공급유형}(일반)"`으로 분리하여 각각 독립된 레코드로 추출합니다.
  - 예시: 총공급 68호 (우선 34, 일반 34) $\rightarrow$ `supply_type: "행복주택(우선)", supply_count: 34`, `supply_type: "행복주택(일반)", supply_count: 34`
  - 예비입주자만 있는 주택형의 경우 `"{공급유형}(일반)"` (또는 `"{공급유형}"`)으로 `reserve_count`를 배정합니다.
- **호실 단위 세대수 원칙**: 호실 번호(`room_number`)가 존재하는 물리적 개별 방은 **무조건 `supply_count = 1, reserve_count = 0`**. 주택군 전체 예비자수는 `recruitment_groups[].reserve_count`에만 기록.
- **`room_number`(동/호수) 형식**: 원문 표기를 그대로 `"2401동 105호"`처럼 동+호 붙여쓰기로 기록. 동/호 중 하나만 있으면 있는 것만 기록. 개별 호실 지정이 없는(묶음 모집) 유닛은 비워둡니다.
- **`room_count`(방 개수)**: 원문 평면도/타입표에 방 개수(안방+침실 수)가 명시된 경우에만 정수로 기록. 원문에 없으면 추정하지 말고 비워둡니다.
- **`contract_area`(계약면적)**: 원문 표에 전용면적과 별도로 계약면적/공급면적이 명시된 경우에만 기록(제곱미터). 전용면적만 있는 표라면 비워두고 `exclusive_area`만 채웁니다 — 전용면적을 계약면적에 임의로 복사하지 마십시오.
- **`attributes`(비정형 사업유형 설명)**: "10년 공공임대주택리츠 예비입주자 모집"처럼 해당 유닛이 속한 사업/프로그램을 한 줄로 설명하는 원문 문구가 있으면 기록. `supply_type`/`target_group`으로 이미 구조화된 정보를 중복 기재하지 않습니다.
- **금액 단위**: 기본 보증금(`deposit`) 및 월임대료(`monthly_rent`)는 **100% 원 단위**로 환산 기록. (천원 단위 착오 절대 금지)
- **상호전환 한도 동적 계산**:
  - 전세형(준전세) 등 증액 불가 공고: `max_deposit = deposit`, `min_monthly_rent = monthly_rent` 대입, 감액 전환만 계산.
  - 전환 불가/미기재 시: 4개 필드 모두 기본값(`deposit`, `monthly_rent`) 대입.
- **공급대상 정규화**: `target_group`은 `"청년", "신혼부부", "다자녀", "고령자", "주거약자", "일반", "상관없음"` 표준화.
- **단지 연계**: `complex_name`과 `complex_address`는 상위 `complexes` 레코드와 1:1로 문자열이 완벽히 일치해야 함.

#### ⑥ `details` (7대 표준 카테고리 프리미엄 수록 규약 - 컴팩트 다이어트 및 가독성 최적화)
사용자가 원본 PDF를 다시 열지 않아도 청약의 모든 조건을 일목요연하게 파악할 수 있도록 작성하되, 웹/모바일 아코디언 UI에 최적화된 **간결한 구조**를 유지합니다.

⚠️ **[절대 금기 사항 - 아코디언 본문 최상단 중복 대제목/번호 삽입 금지]**:
- `section_title`이 UI 아코디언 헤더(예: `6. 선정 및 배점 기준`)로 이미 표시되므로, **`section_content` 본문 최상단에 `#`, `##`, `### N. 제목` 같은 중복 대제목과 어긋난 번호를 절대 넣지 마십시오**.
- 본문은 불필요한 타이틀 없이 곧바로 서두 요약, 표, 또는 소주제(`#### 1. 세부 요건`)부터 바로 시작해야 합니다.

⚠️ **[절대 금기 사항 - `section_title` 필드 자체에 번호 삽입 금지]**:
- `section_title`은 반드시 **순수 제목 문자열만** 저장해야 합니다 (예: `"신청 자격 요건"`). `"1. 신청 자격 요건"`처럼 앞에 번호를 붙이지 마십시오.
- 번호는 프론트엔드(`AnnouncementCard.tsx`)가 `sort_order` 기준으로 자동 부여하므로, `section_title`에 번호가 섞여 들어오면 화면에 `"2. 1. 신청 자격 요건"`처럼 번호가 두 번 표시되는 버그가 발생합니다 (실측 사례: 2026-09-20, 15개 공고·99개 행에서 발생해 `009_strip_section_title_numbering.py`로 정정함).

⚠️ **[분량 다이어트 규격]**:
- 장황한 법조문 문장이나 행정 수식어를 전면 제거하고, 핵심 조건(`자격`, `소득`, `자산`, `청약통장`)을 간결한 **불렛포인트(Bullet)**로 압축합니다.
- 섹션당 목표 분량은 **400~1,000자 내외 (전체 총 5,000~6,000자 수준)**로 스크롤 압박을 대폭 줄이면서 마크다운 표의 가독성을 극대화합니다.

1. **`'모집단위별 공급 및 예비자 현황'`** (`sort_order: 1`):
   - 공고문 원본의 모든 모집단위(단지/주택군)명, 공급(우선/일반), 예비자수를 컴팩트하게 정리한 마크다운 총괄표 수록.
   ```markdown
   | 모집단위(단지명) | 지역 | 공급유형 | 우선공급 | 일반공급 | 예비자수 | 합계 |
   | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
   ```

   ```markdown
   | 가구원수 | 100% 이하 | 120% 이하 | 140% 이하 | 비고 |
   | :--- | :--- | :--- | :--- | :--- |
   | 1인 가구 | 3,353,884원 | 4,024,661원 | 4,695,438원 | 1인 (+20%p 가산) |
   ```

4. **`'임대 조건 및 융자 혜택'`** (`sort_order: 4`):
   - 임대기간, 최장 거주기간, 보증금-월세 상호전환 공식/이율(증액 연 6%, 감액 연 3.5% 등), 전환 한도 명시.

5. **`'선정 및 배점 기준'`** (`sort_order: 5`):
   - 입주자 선정 순위(1순위, 2순위, 3순위) 및 **공식 배점 기준표(가점표, 주거약자 배점표) 마크다운 표 100% 필수 수록**.
   ```markdown
   | 평가 항목 | 배점 기준 | 증빙 서류 |
   | :--- | :--- | :--- |
   | 수급자 여부 | 생계·의료수급자(3점), 주거수급자/차상위(2점) | 수급자증명서 |
   ```

6. **`'신청 방법 및 제출 서류'`** (`sort_order: 6`):
   - 다중 단지(매입임대)의 경우: **[주택군 신청 → 순번 부여 → 실물 열람 → 동호지정 계약]** 안내 박스 필수 수록.

   - 접수처 URL/장소, 공통 구비 서류 및 대상자별 추가 증명서류 목록 전수 수록.

   - 예비자 지위 유효기간, 보수 중 주택, 주차 협소, 불법 전대 처벌 규정, 중복 청약 제한 등.
