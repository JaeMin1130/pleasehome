# Skill: audit-data (공고 데이터 전수 검수 및 최종 적재 파이프라인)

이 스킬은 `extract-data` 에이전트가 생성한 `data.json`이 공고문 원본(`document.md`) 및 `api_meta.json`과 **단 1개의 컬럼 오차도 없이 100% 무결한지 독립적으로 전수 감사(Full-Audit)**하고, 합격 리포트 발행 후 SQLite DB에 안전하게 최종 적재하는 검수·적재 통합 가이드라인입니다.

⚠️ **절대 주의 (감사자 철칙)**:
- **[서브에이전트 독립 감사 원칙 (Mandatory Independent Subagent)]**: 메인 에이전트는 메인 세션에서 감사를 직접 흉내 내거나 셀프 검증할 수 없으며, 반드시 `invoke_subagent`를 통해 `audit-data` 전용 독립 서브에이전트를 호출하여 1:1 전수 감사를 수행해야 합니다.
- 감사자는 절대로 스스로 데이터를 날조하거나 지레짐작으로 승인해서는 안 됩니다.
- 아래 **6대 테이블 전 컬럼 체크리스트 중 단 1건이라도 불합격이 발생하면 즉시 불합격 사유를 출력하고 DB 적재를 영구 차단(반려)**해야 합니다.

## 1. 6대 테이블 전 컬럼 1:1 대조 체크리스트

### ① `announcements` (공고 기본 메타)
- [ ] `title`: `[정정공고]`, `[정정]`, `(정정)`, `[재공고]` 등 시스템 접두사 노이즈가 100% 제거되었는가?
- [ ] `institution`: `LH`, `SH`, `GH`, `iH`, `HUG`, `민간` 중 1개로 정확히 표준화되었는가?
- [ ] `subscription_type`: `매입임대`, `행복주택`, `국민임대`, `영구임대`, `공공분양`, `장기전세` 등 표준 유형인가?
- [ ] `region`: 대한민국 17대 표준 광역지자체명인가? (비표준 지자체명 영구 차단)
- [ ] `dtl_url`: `api_meta.json`의 원본 PC 공고 URL과 일치하며 깨지지 않았는가? **(정정공고의 경우 구버전 링크가 아닌 정정공고 `api_meta.json`의 최신 URL인가?)**
- [ ] `dtl_url_mob`: 모바일 공고 URL이 최신 정정공고 URL로 유효하게 들어있는가?
- [ ] `doc_path`: 실제 `document.md` 상대 경로와 100% 일치하는가? (정정공고 폴더 경로 확인)
- [ ] **[누적 규칙 #8 ID 보존 검증]**: 기적재 정정공고의 경우 기존 공고 식별자(`announcements.id`)와 단지 식별자(`complexes.id`)가 영구 보존되는가? (URL 및 외부 참조 보호)

### ② `announcement_schedules` (공고 일정)
- [ ] `schedule_type`: `신청접수`, `서류제출대상자발표`, `서류제출`, `당첨자발표`, `계약체결` 5대 구분이 원문과 매핑되었는가?
- [ ] `start_date` / `end_date`: `YYYY-MM-DD HH:MM:SS` 형식이며 공고문 본문 일정표의 일자/시간과 초단위까지 일치하는가?
- [ ] 순위별 접수기간: 1순위와 2순위 접수일이 다른 경우 notes 등에 명확히 분리 기록되었는가?

### ③ `announcement_recruitment_groups` (모집단위 / 주택군)
- [ ] `name`: 공고문 공식 주택군/모집단위명과 100% 일치하는가?
- [ ] `supply_count`: `sum(recruitment_groups.supply_count) == 공고문 서두 총 공급호수(공가)` 1:1 일치 여부
- [ ] `reserve_count`: `sum(recruitment_groups.reserve_count) == 공고문 서두 총 모집 예비자수` 1:1 일치 여부
- [ ] Name-Identity Guard: 단지명이 모집단위명과 동일한 경우 다른 단지가 종속되어 있지 않은가? (1:1 매핑 확인)

### ④ `complexes` (단지 정보 - 단지명 오염 원천 차단)
- [ ] `name`: **단지명이 `17(병점동)`, `9(동천동)`, `22(당동)` 같은 지번/도로명 끝 번호/동 번호 찌꺼기로 오염되지 않았는가?** (원문 표의 공식 단지명/블록명과 1:1 대조 확인)
- [ ] `address`: 실제 지번/도로명 상세주소가 완전하게 들어있는가?
- [ ] 물리적 분리: 서로 다른 도로명주소 건물이 개별 독립 complex로 분리되었는가?
- [ ] `heating_type`: `개별난방`, `지역난방`, `중앙난방` 등 원문 표 기재 내용과 일치하는가?
- [ ] `has_elevator`: 승강기 유무(True/False)가 원문 표와 일치하는가?
- [ ] `parking_info`: 본문/유의사항에 언급된 주차 정보(주차대수, 협소 안내 등)가 채워져 있는가? (이유 없이 NULL 방치 차단)
- [ ] **[`complex_type` 임의 의역 금지 검증]**: 원문 표에 건물유형/사업유형이 명시되어 있는데 `아파트/연립주택/다세대주택` 등으로 임의 의역하지 않고 원문 표기 그대로 적재되었는가? (실측 사례: 같은 건물이 서로 다른 시점에 "연립주택"/"다세대주택"으로 각각 의역되어 재적재 시 충돌 발생 — 표 헤더가 애매해도 원문 값을 훼손하면 즉시 FAIL)

### ⑤ `housing_units` (유닛 조건)
- [ ] **[`room_type` 컬럼 오추출 검증]**: 원문 표에 `순번`(행 번호) 컬럼과 평형/타입 구분 컬럼(`신청유형`/`주택형`/`공급형별`/`주택타입`/`평형` 중 하나)이 둘 다 있는 경우, `room_type`에 순번 값이 잘못 들어가지 않았는가? (같은 `room_type` 값을 가진 유닛들의 `exclusive_area`가 서로 터무니없이 다르면[예: 한 "1형"이 18㎡~34㎡을 다 가리킴] 순번 오추출 의심 — 즉시 FAIL)
- [ ] **[우선공급/일반공급 분리 검증]**: 원문 표에 공급호수가 `우선`과 `일반`으로 구분되어 있는 경우, `supply_type`이 `"{공급유형}(우선)"`과 `"{공급유형}(일반)"`으로 분리되어 각각의 공급호수가 독립 레코드로 적재되었는가? (합산하여 뭉갰을 경우 즉시 FAIL)
- [ ] `supply_count` / `reserve_count`: 호실 번호(`room_number`)가 있는 개별 방은 무조건 `supply_count = 1, reserve_count = 0`인가?
- [ ] `deposit` / `monthly_rent`: 기본 보증금과 월임대료가 **100% 원 단위(실금액)**로 환산되었는가? (천원 단위 착오 0건 확인, 단 분양형은 `sale_price`에 분양가가 기록되고 `deposit`/`monthly_rent`는 0이어도 무방)
- [ ] 상호전환 한도:
  - 전세형(준전세) 등 증액 불가 공고: `max_deposit == deposit`, `min_monthly_rent == monthly_rent`로 처리되었는가?
  - 일반 공고: 공고문 공식(이율 연 6%, 감액 연 3.5% 등)이 적용되었는가?
- [ ] `target_group`: `청년, 신혼부부, 일반, 다자녀, 고령자, 주거약자, 상관없음` 표준 규격명인가? (복수 자격을 쉼표로 나열하는 건 허용 — 적재 시 자동으로 태그 분해됨)
- [ ] `income_group`: 원문의 순위/임대조건 시세비율/소득기준 표현이 임의로 요약되거나 숫자 하나로 뭉개지지 않고 원문 그대로 보존되었는가?
- [ ] **[`recruitment_group` 유닛별 지정 검증]**: 한 단지 안에 서로 다른 신청단위(예: 일반 배정 vs 리츠형 배정)가 섞여 있는 경우, 단지 기본값이 아니라 유닛별로 올바른 `recruitment_group`이 지정되었는가?
- [ ] 단지 FK 연계: 모든 유닛의 `complex_name`과 `complex_address`가 `complexes` 테이블 레코드와 1:1 매칭되는가?

### ⑥ `announcement_details` (상세 요건 7대 카테고리 프리미엄 검수 - 진위 검증 및 가독성)
- [ ] **[내용적 진위 검증 (Semantic Truthfulness) - 날조 0건 확인]**:
  - `소득 및 자산 기준`: 본문의 소득 금액표 및 자산 기준이 해당 공고문 원본(`document.md`)의 수치와 1:1로 일치하는가?
  - `선정 및 배점 기준`: 해당 공고의 공식 가점 기준표 항목과 배점 수치가 원본과 완벽히 일치하는가?
  - `공고 유형 본질 일치`: 든든전세(100% 추첨, 소득/자산 무관)에 일반 소득표나 가점표가 날조되어 들어가지 않았는가? 행복주택 완화 공고에 일반 기준이 들어가지 않았는가?
- [ ] **[원본 출처 라인 번호 증빙 확인]**: 각 섹션 상단에 `document.md`의 실제 원본 출처 라인(`<!-- Source: document.md#L... -->`)이 명시되어 있는가?
- [ ] **[아코디언 본문 최상단 중복 대제목/번호 0건 확인]**: 7개 섹션 본문 최상단에 `#`, `##`, `### N. 제목` 형태의 중복 헤더가 단 1개라도 있는가? (적발 시 즉시 FAIL)
- [ ] **[정량적 적정 분량 규격]**: 7대 섹션 전원 글자 수 **400자 이상 1,500자 이하** 범위 내에서 핵심 불렛포인트 위주로 컴팩트하게 정리되었는가?
- [ ] **[마크다운 표 필수 포함 규격]**:
  - `모집단위별 공급 및 예비자 현황`: 우선공급, 일반공급, 예비자수가 분리된 컴팩트 총괄표 (`|---|`) 필수 포함
  - `소득 및 자산 기준`: 원본에 근거한 가구원수별 소득표 및 자산/자동차 기준 마크다운 표 (`|---|`) 필수 포함 (소득 배제 공고는 사유 명시)
  - `선정 및 배점 기준`: 원본에 근거한 계층별 순위 및 가점 배점표 마크다운 표 (`|---|`) 필수 포함 (추첨제 공고는 추첨 방식 명시)
  - `신청 방법 및 제출 서류`: 매입임대 단계별 절차 안내 박스 (`>`) 또는 제출서류 표 필수 포함

## 2. 정량적 절대 불합격(Hard FAIL) 기준

감사자는 아래 조건 중 단 하나라도 해당되면 **즉시 불합격(FAIL)** 처리하고 세 번째 에이전트(적재)로 넘겨서는 안 됩니다:
1. `공고문 원문 총 공급호수(공가)` $\neq$ `sum(recruitment_groups.supply_count)` 또는 $\neq$ `sum(housing_units.supply_count)`
2. `공고문 원문 총 예비자수` $\neq$ `sum(recruitment_groups.reserve_count)`
3. 원문에 `우선`과 `일반` 공급호수가 나뉘어 있는데 `housing_units`에서 이를 합산하여 1개 레코드로 뭉갠 경우
4. `complexes.name`에 지번, 건물번호, 동 번호 찌꺼기(`17(병점동)`, `9(동천동)` 등)가 1건이라도 포함된 경우
5. `announcement_details` 7개 섹션 중 내용 글자 수가 400자 미만이거나, 본문 최상단에 `#`, `###`류 중복 대제목/번호가 삽입되어 있는 경우, 또는 소득/가점/총괄 섹션에 마크다운 표가 누락된 경우
6. `housing_units.deposit` 또는 `monthly_rent`가 원 단위가 아닌 천원 단위로 기재된 경우
7. 정정공고임에도 구버전 공고의 만료된 `dtl_url`을 그대로 방치하거나 최신 정정 URL/문서 경로(`doc_path`)로 갱신되지 않은 경우
8. **[날조 데이터 적발 시 즉시 영구 탈락]**: `announcement_details`가 원본 `document.md`에 근거하지 않고 임의의 합성 템플릿으로 날조되었거나, 공고 유형 본질(든든전세 추첨제, 소득완화 등)과 다른 거짓 데이터가 들어간 경우
9. **[비인가 스크립트·배치 적발 시 즉시 탈락]**: `scratch/` 등 임의 스크립트로 생성되었거나, 다건 일괄 배치 처리로 검증을 우회한 흔적이 있는 경우
10. 같은 `room_type` 값을 가진 유닛들의 `exclusive_area`가 서로 크게 벌어져(순번 오추출 의심 패턴) 있는데 원문 대조 없이 그대로 통과시킨 경우
11. 원문 표에 건물유형/사업유형이 명시되어 있는데 `complex_type`이 그 표기 대신 감사자/추출자가 임의로 의역한 값(아파트/연립주택/다세대주택 등)으로 바뀐 경우

## 3. 감사 증빙 리포트 필수 출력 템플릿

감사 에이전트는 감사를 완료한 후, 반드시 아래 양식의 **`전수 감사 증빙 리포트`**를 화면에 출력해야 합니다. 추상적인 구두 승인은 무효입니다:

```markdown
# 📋 공고 전수 감사 증빙 리포트: [{공고ID}] {공고제목}

## 1. 수치 정합성 대조표
| 검증 항목 | 공고문 원문(document.md) | 추출 데이터(data.json) | 일치 여부 | 판정 |
| :--- | :--- | :--- | :--- | :--- |
| 총 공급호수(공가) | 120호 | 120호 | 일치 | PASS |
| 총 모집 예비자수 | 360명 | 360명 | 일치 | PASS |
| 주택군(모집단위) 수 | 5개 군 | 5개 군 | 일치 | PASS |
| 단지(complexes) 수 | 18개 주소 | 18개 주소 | 일치 | PASS |
| 유닛(units) 총수 | 120개 호실 | 120개 호실 | 일치 | PASS |

## 2. 단지명 오염 전수 검사
- 오염 단지명 검출 건수: 0건 (17(병점동)류 찌꺼기 전수 제거 확인)
- 단지 스펙(난방, 엘리베이터, 주차정보) 충실도: PASS (결측치 0건)

## 3. announcement_details 7대 섹션 정량 검사
| 카테고리 | 글자 수 | 마크다운 표 포함 여부 | 판정 |
| :--- | :--- | :--- | :--- |
```

### [불합격(FAIL) 판정 시]
1. **토큰 발급 절대 금지**: `audit_passed.token`을 절대 생성하지 않습니다.
2. **메인 직접 개입 엄단**: 메인 에이전트는 결함을 임의로 메인 세션에서 직접 수정해서는 안 됩니다.
3. **재수정 위임 루프**: 메인 에이전트는 감사 리포트의 불합격 사유를 프롬프트에 담아 `invoke_subagent(extract-data)`를 재호출하여 결함 데이터를 정밀 수정한 후 감사를 다시 받아야 합니다.
