# Git Commit Message Convention

이 프로젝트에서 Git 커밋을 남길 때는 아래의 **Conventional Commits** 컨벤션을 반드시 엄격하게 준수해야 합니다.

---

## 1. 커밋 메시지 기본 구조

```text
<type>(<scope>): <subject>

<body>

<footer>
```

*   **`<type>` (필수):** 소문자로 표기하며, 커밋의 본질적인 성격을 정의합니다.
*   **`<scope>` (선택):** 변경 사항의 도메인/범위를 명시합니다. (예: `db`, `parser`, `api`, `ui`)
*   **`<subject>` (필수):** 동사 원형/명령조로 시작하며, 50자 이내의 한 줄 요약입니다. 끝에 마침표(`.`)를 찍지 않습니다.
*   **`<body>` (선택):** 무엇을 왜 수정했는지 상세 기술이 필요할 때 작성합니다.
*   **`<footer>` (선택):** 이슈 추적 ID 연동이나 하위 호환성을 깨뜨리는 `BREAKING CHANGE` 정보를 기록합니다.

---

## 2. 허용되는 커밋 타입 (`type`)

| 타입 | 설명 | 예시 |
| :--- | :--- | :--- |
| **`feat`** | 새로운 기능 추가 | `feat(api): 입주자 공고 필터링 API 기능 구현` |
| **`fix`** | 버그 수정 | `fix(db): DB 커넥터 누수 버그 해결` |
| **`docs`** | 문서 작성 및 수정 (README, 가이드 등) | `docs: README.md에 실행 절차 업데이트` |
| **`style`** | 코드 스타일 수정 (포맷팅, 세미콜론 누락, 미사용 변수 정리 등) | `style: lint 규칙에 맞춰 코드 들여쓰기 보정` |
| **`refactor`** | 리팩토링 (기능 추가나 버그 수정이 없는 구조적 개선) | `refactor(parser): JSON 파서 모듈 재사용 구조 개선` |
| **`test`** | 테스트 코드 작성 및 수정 | `test(db): DB 정합성 감사 스크립트 기능 테스트 작성` |
| **`chore`** | 패키지 설정, 빌드 시스템 수정, gitignore 수정 등 잡무 | `chore: .gitignore에 가상환경 예외 규칙 보완` |
| **`perf`** | 성능 개선을 위한 코드 수정 | `perf(map): 지도 렌더링 성능 최적화` |

---

## 3. 작성 팁 및 원칙

*   **한글로 작성 시:** 타입은 항상 영어 소문자로 표기하고 제목은 한글로 간결하게 명시합니다. (예: `feat(db): ...`)
*   **영어로 작성 시:** 과거형(`added`, `fixed`) 대신 동사 원형(`add`, `fix`)을 사용합니다.
*   **일관성 유지:** 작업 범위를 명확히 분리하여 하나의 커밋에는 가급적 하나의 타입 단위 작업만 포함하도록 합니다.
